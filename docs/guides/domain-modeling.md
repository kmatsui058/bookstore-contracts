# モデリングガイドライン

このドキュメントは[ドキュメント作成ガイドライン](/guides/documentation.md)に準拠する必要があります。

_[ガイドラインに戻る](./README.md)_

ドメインモデル（LikeC4 のモデルとそのビュー）を書き・レビューするときに従うものです。「守ること」に挙げた項目は必ず守り、それ以外は指針として扱ってください。

## ドキュメントの位置づけ

ドメインモデルは、あらゆる設計ドキュメントの最上位に位置し、ビジネス要件の権威ある単一情報源（SSOT）です。API の定義・仕様書・実装は、モデルに定義された語を使います。

## 基本設計原則

YAGNI と単一責任原則に従います。ドメインモデルはビジネスの本質だけを表し、技術的な詳細を含めません。

## モデル

ユビキタス言語は、[LikeC4](https://likec4.dev/) で記述したモデル（`.c4` ファイル）を単一情報源として管理します。語（ユビキタス言語の用語として定義する要素）・属性・関係はすべてモデルで定義します。

要素は入れ子で置き、最上位の要素からその要素までの入れ子の経路を「所有の階層」と呼びます。関係の種類は、観点ごとに「次元」にまとめます。次元はデータ（`data`。型・継承・参照）・イベント（`event`。コマンドとイベントの連鎖）・状態（`state`。状態の遷移）・戦略（`strategy`。コンテキストどうしの統合パターン）の4つです。

### 置き場所と記述

- モデルのルートは `docs/domain/` とする。要素と関係の種類（`spec.c4`）、次元（`global.c4`）、コンテキストマップ（業務ドメイン・コンテキストの要素と、戦略の次元の関係）は直下の `.c4` ファイルに書く
- 各コンテキスト・モジュールの `.c4` ファイルは、そのコンテキスト・モジュールのディレクトリ（英名をケバブケースにした名前）に置く。ビューは、描く要素を宣言しているファイルに書く
- コンテキスト・モジュールの概要と責務は、その要素の `description` に書く
- コンテキストどうしの関係は戦略の次元の関係で書き、コンテキストをまたぐ語どうしの関係（イベントの購読など）も、その次元に属する関係の種類で書く。どちらを描くかはビューで次元を選んで絞り込む
- モデルの要素の定義ではない文章は、モデルに入れず Markdown に書く

### 守ること

- 最上位には「書店の業務」の要素を置き、その下に業務ドメイン、その下に境界付けられたコンテキストを置く。書店の外のコンテキストは、種類「外部コンテキスト」の要素として最上位に置く。書店のものはすべて「書店の業務」の中にあるので、ディレクトリの階層と、ビューの ID・タイトルにはその層を入れない
- 語は、その責務を持つものの下に入れ子で置く。どのモジュールの責務でもなく、モジュールをまたいで使う語は、そのコンテキストの共通語彙のモジュール（ディレクトリは `shared`）に置く
- ほかのコンテキストの語（識別子・イベントなど）は、それを使う側のコンテキストの語として定義し、どのコンテキストのものかを書く
- 1つの境界付けられたコンテキストの中で、同じ名前（和名・英名のどちらでも）が別の語を指してはならない。衝突したらモデリングの誤りとして直す（別のコンテキストに同じ名前の語があるのはよい。属性の名前は、持ち主が違えば同じでよい）
- 要素の ID は、改名しても変えない。ID は、正式な名前ではないと一目で分かる略記にし、英数字だけで大文字を続けずに書く。次元の英名（`data`・`event`・`state`・`strategy`）は ID に使わない
- 和名は `title`、英名は `summary` に書く。英名は略語の大文字を保つ camelCase とし、業務ドメイン・コンテキスト・モジュールと語は大文字、属性は小文字で始める（属性が略語で始まるときは、その略語を小文字にする）
- 業務上の識別子（集約やエンティティを特定する値）は値オブジェクトとして定義し、何を特定するかを説明に書く。外部コンテキストの識別子も値オブジェクトにする
- 要素と関係の種類は `spec.c4`、次元（関係の種類の分類）は `global` の `predicateGroup` にだけ定義する。関係には必ず種類を付ける。関係の種類を足すときは、4つの次元のどれか1つに加える
- 属性は、それを持つ語の子要素として定義する。型がモデルの語なら `typeOf`、その一覧なら `listOf` の関係を張り、基本型は `metadata.type` に大文字で始まる英名で書き、基本型の一覧は `List<型名>` と書く。属性の制約は `description` に書く
- 列挙型の値は、列挙型の子要素（種類 `enumValue`）として定義し、API でやり取りする値そのものを ID、和名を `title` に書く。値は契約そのものなので、上の ID と英名のルールはすべて当てはめず、英名は書かない。値の要素にはビューを作らない。値が LikeC4 の ID に使えない文字を含むときは、使えない文字を置き換えた ID にし、API でやり取りする値そのものを `metadata` の `value` に書く

### 更新の手順

- ユビキタス言語の変更は、まずモデルに反映し、そのあと関連するビューを直す
- モデルに定義されていない語を、ほかのドキュメントや API で使わない。新しい語は先にモデルに足す
- 変更は Pull Request でレビューし、同じコンテキストの別モジュールとの名前の衝突と、モデルとほかのドキュメントの整合を確かめる

## ビュー

ドメインモデルの入口は LikeC4 のビューです。ビューは関係を見るために作ります。コンテキストマップ・イベントフロー図・ステートマシン図は、それぞれ戦略・イベント・状態の次元で関係を切り出したビューとして、所有の階層のどの要素についても必要に応じて作ります。

持ち物のツリー（どのモジュールに何があり、集約がどの属性・コマンド・イベントを持つか）はビューにせず、要素の詳細の Structure で見ます。

### 守ること

- 属性の型の線（`typeOf`・`listOf`）は、語の要素のビューでだけ描く
- 要素のビュー（1つの要素を描くビュー）と次元ごとのビューの ID は、所有の階層の ID を、先頭以外の大文字の前にハイフンを入れて全体を小文字にしたうえで `_` でつなぐ。次元ごとのビューは、その末尾に次元の英名を `_` でつなぐ
- それらのビューのタイトルは、所有の階層の和名を ` / ` でつなぐ。次元ごとのビューは、その末尾に次元の和名を ` / ` でつなぐ。下の階層にもビューがある要素のビューは、末尾に「和名（種類）」を ` / ` でつなぐ
- `description` の中からビューへは、`#/view/<ビューID>/` の形でリンクする
- 特定の要素に対応しない横断的なビュー（サガなど）の ID とタイトルは自由に付けてよい
